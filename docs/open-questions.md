# Open questions

Things nobody has nailed down. Ordered by how much they would improve a driver.

## 1. The `0300` calibration record is undecoded (highest value)

Command `03 00` returns 66 bytes, identical on every read from a given unit. It is
described as eight packed vec3 entries plus a temperature, with each vec3 being
big-endian 21-bit-per-axis plus one padding bit:

```
0   8 bytes  accelerometer bias?
8   8 bytes  gyroscope bias?
16  8 bytes  accelerometer alignment row X?
24  8 bytes  row Y?
32  8 bytes  row Z?
40  8 bytes  gyroscope alignment row X?
48  8 bytes  row Y?
56  8 bytes  row Z?
64  2 bytes  temperature at calibration time (i16 LE)
```

**Nobody has applied it to raw data and shown it helps.** The evidence that this
layout is right is weak: it makes the arithmetic come out to exactly 64 bits, and
the Samsung APK calls these "bias" values. High entropy and non-decodability as
int16/float32 at naive strides is consistent with 21-bit packing but does not
prove it.

**Why it matters:** every existing driver works around missing calibration with
hand-rolled hacks — `gearVRC` estimates gyro bias online when stationary, `cwig`
invents a min/max figure-8 magnetometer cal. If the factory calibration is
readable and usable, drift improves for free and the magnetometer stops being
"unusable without calibration".

**Concrete plan:** dump the record from at least three units. If the 21-bit
hypothesis is right, each 8-byte group should decode to three plausible values in
the 21-bit signed range and the pad bit should always be 0. Then check whether the
8 "rows" form two 3×3 matrices that are approximately rotation-like/scale-like.
Then apply and measure drift against an unaided run.

## 2. Exact IMU part number

Sensitivity gives it away as an ST 6-axis at ±16 g / ±2000 dps (2048 LSB/g,
14.285 LSB/dps), but the marking has never been photographed clearly enough to
confirm. Candidates: LSM6DS3, LSM6DSL, LSM9DS-family. Guessed as "LSM9DS3" in one
writeup (which is not a real ST part number, suggesting a memory error).

Matters because the datasheet would give the real noise density, the actual
sensitivity tolerance, and whether there is an embedded sensor hub or FIFO we
could enable via the SoC.

## 3. Exact touchpad controller and how `SS` is generated

The `SS` field (bits 5:4 of byte 54) reports touching / not-touching / just
lifted. Whether "just lifted" is genuinely generated by the touch controller or
inferred by firmware is unknown. Also unknown: whether the pad supports
multi-touch, pressure, or hover. The `0500` settings record exposes only a
binary button mask (`0b111111`), which implies the firmware models the pad as a
single contact.

## 4. Magnetometer scale and axis alignment

`~0.06 µT/LSB` is a number inherited from jsyang and carried forward by everyone;
it has never been independently derived. The hard-iron offset is large
(X ≈ +6000 raw) and unit-specific.

The −30° board-rotation correction is an empirically fitted constant from
`cwig`, derived from one unit. Whether 30° is a design value (a nice round angle,
suggesting yes) or a fit artifact is unknown. It is not a datasheet number.

**Concrete plan:** proper tumble calibration on a non-magnetic bench, compare
fitted ellipsoid to the −30° hypothesis, and check whether the rotation is exactly
30° or whether it varies unit to unit.

## 5. Conflicting axis conventions

Two mutually incompatible descriptions exist:

- **dennisonbertram (verified against gravity in known poses):** right-handed,
  **+X right, +Y forward (toward trigger), +Z out of the touchpad face.** Gyro
  same axes, right-hand rule: turn left → +Z, raise nose → +X.
- **uutzinger's gearVRC (from raw observation):** raw accel X points *left*, Y
  points *toward the user*, Z points *down*; and he applies the permute
  `acc −Y−X+Z`, `mag −X+Y+Z`, `gyr +Y+X−Z` to reach an x-forward/y-east/z-down
  frame.

These could both be true if the second is describing raw silicon axes before any
remap and the first is describing the final convention, but the sign flips
(−Y, −X) do not reduce to a pure rotation of the same vector — the permutation is
cyclic-ish (Y,X swap plus negation), which is a rotation combined with a
reflection unless one of the signs is different from what is written.

**Status:** the driver has a configurable axis map (`gearvr-fusion`), but the
default is still the documented guess. This remains a hardware task.

**Concrete plan:** with the driver running, hold the controller in a known pose
(flat on the desk, pointing at a wall) and log raw accel. Gravity alone resolves
Z. Then rotate 90° about each axis to resolve X and Y. This takes 20 minutes and
should be step one of implementation because every downstream fusion result
depends on it.

## 6. What "VR Mode" actually negotiates, and whether rate can exceed 68 pkt/s

`08 00` requests connection interval 11 (13.75 ms), which yields ~68 pkt/s with
3 samples each. 13.75 ms is the BLE minimum for a non-2M-PHY connection.

Open questions:

- Does the DA14681 support BLE **2M PHY**? If so, a host could request it and
  possibly run faster. BLE 4.2 theoretically includes 2M PHY (it was introduced in
  Bluetooth 5.0 for LE 2M, so **no** — the controller is 4.2 and cannot).
- The DA14681's own IMU sample interval from the settings record is **5 ms**
  (~200 Hz), matching the observed ~206 Hz. So we are probably already at the
  device's internal limit, and 68 pkt/s is the ceiling. Worth confirming.
- The 30-second disconnect-if-parameters-not-negotiated behaviour has been
  observed but the exact trigger conditions are unclear.

## 7. Is the 66-byte and 40/68-byte reply reliable across firmware versions?

Record layouts were characterized on `YO324XXU0AQC1` (and partly `AQD4`). One
field is the firmware revision expressed as an **ASCII fragment** (`"QC1\0"`) on
one version and as a **number** (`3425361`) on another. The numeric form on AQD4
is the little-endian bytes `"QD4\0"`, so both can be read as ASCII. The parser
stores the raw bytes and exposes both `firmware_ascii()` and
`firmware_numeric()`.

Unknown: whether `AQBG` units (rare firmware) differ further.

## 8. Power consumption and realistic battery life at 68 pkt/s

Samsung claimed good battery life on AAA cells, but VR mode streaming at 68 pkt/s
is presumably the heaviest load. No one has measured current draw in each mode.
Relevant if you plan to leave the driver running continuously.

## 9. Whether the controller can be made not to sleep

Everyone agrees keep-alives (`04 00`) do not prevent inactivity sleep. But the
definition of "activity" is not precisely characterized: does touchpad *hover* (if
the pad detects it) count? Does IMU motion count? uutzinger reports disconnects
"also when the device is just moved around", suggesting movement alone is not
enough and only button/touch events reset the timer.

If button events are what matters, a driver could not synthesize them — there is
no command to inject a fake press. So we must design around sleep, not prevent it.

## 10. What "User Calibration Mode" in the firmware strings does

Firmware strings reference a user calibration mode. Possibly reachable via a
command in the `09`–`10` range (all of which are currently ignored), or a button
combo. Nobody has found the trigger. If it is the magnetometer calibration flow,
that would replace a lot of hand-rolled code.

## 11. Whether SUOTA can be repurposed

Since SUOTA payloads are **unsigned** and downgrade is accepted, one could in
principle flash a custom DA14681 firmware that speaks standard HID-over-GATT, or
that stops sleeping, or that streams faster. This is a real option, not a fantasy
— the tooling exists (Dialog's app, and the SDK is public). It is also the
fastest route to a bricked controller, and it is out of scope for this project.
Worth a doc and maybe an experiment on a sacrificial unit.

## 12. Steam Deck specifics

**Partially answered (2026-10-19).** On Bazzite 44 / Fedora 44 with Steam running,
a synthetic `uinput` gamepad (`1209:0001`) was enumerated, opened by Steam, given
an SDL mapping, and assigned `configset_controller_generic.vdf`. The udev-259
generic-pad regression did not reproduce there. Still untested: a user-service
instance on SteamOS 3.x specifically, and whether a virtual DualSense is
accepted with gyro. See [`implementation.md`](implementation.md).
